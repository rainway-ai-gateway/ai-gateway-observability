# TC-02 消费打平

## 用例编号与名称

TC-02 消费打平

## 所属场景

CLICKHOUSE01 ClickHouse 对接（报表存储新引擎）

## 版本声明

- `ai-gateway-observability`：当前源码版本（v0.8 ClickHouse 对接）
- `ClickHouse`：本机 WSL2 单文件 26.10.1.1149
- `Kafka`：本机 WSL2 KRaft 单节点 4.3.1（`environment/kafka-installation.md`）

## 测试目的

验证导入链路（等价 Doris Routine Load 的 COLUMNS 映射）：真实 Kafka 消息经 Kafka 引擎暂存表 + 消费 MV 落入明细表，JSON 打平与 UTC 换算口径全部正确——level 打平十列、限流打平三列、`log_time` UTC 墙钟、logid UInt64 原值保留、Nullable 语义。对应设计稿 §4.1 / §4.2 与修改说明 §6 验证计划 2。

## 运行模式

端到端链路模式：Go 测试经 segmentio/kafka-go 向 Kafka 真实生产三份 demo 样例，ClickHouse Kafka 引擎消费、消费 MV 打平写入明细表，轮询等待后断言。与 doris-it 的差异：doris-it 不生产 Kafka 消息（其 TC02 仅校验 Routine Load 任务创建被接受）；ClickHouse 侧打平发生在 MV 消费路径，必须走真实消费链路。

Kafka 不可达时本用例自动 `SKIP`（其余用例不受影响）。无 Kafka 环境的降级路径（不自动执行，供手工验证）：按 `system.columns` 中 `bfe_ai_log_kafka` 的结构建临时 MergeTree 镜像表（列名带反引号，Nested 物理子列为 `` `req_headers.key` `` 等带点名字），demo JSON 压缩单行后以 JSONEachRow + `input_format_skip_unknown_fields=1` 插入镜像表，再取仓库 `bfe_ai_log_load_mv.sql` 的 SELECT 主体（去注释与 CREATE/TO 头、FROM 换成镜像表）执行 `INSERT INTO bfe_ai_request_log SELECT ...`——与真实消费路径等价。

## 前置条件

1. ClickHouse 已启动，default 无密码可连；Kafka 已启动（`wsl bash /mnt/d/kafka/bin/start-kafka.sh`）。**Kafka 不可达时本用例自动 `SKIP`**（其余用例不受影响）。
2. `clickhouse/demo/` 下 `normal_request.json` / `rate_limit.json` / `auth_reject.json` 存在（本用例期望值来源，兼校验 demo 文件与 DDL 一致性）。

## 测试数据构造

- 独立测试库（同 TC-01），按 setup 顺序建全部 5 对象。
- 独立临时 topic：`<KAFKA_TOPIC>_<纳秒后缀>`（默认基名 `bfe_ai_log_it`），显式建 4 分区（对齐 SQL 资产 `kafka_num_consumers = 3`，分区数小于消费者数会导致空分配、消费不稳定）；配套测试消费组（默认 `clickhouse_bfe_ai_log_it`）。全新 topic + 全新消费组，位点与残留消息无跨运行污染。
- 三份 demo 样例生产前两处改写（均为消息体层面，不改 demo 文件）：
  1. **timestamp 重写为当前时刻**：demo 时间戳为 2026-08-24（epoch 1787538975 等），早于明细表 `TTL log_time + INTERVAL 7 DAY`，直接消费会写入即被 TTL 静默丢弃（不报错、0 行入库）；测试将 `timestamp` 置为生产当刻（三消息相差 10s），其余字段保持 demo 原值，`log_time` 断言以注入值为准。
  2. **压缩为单行**：demo 文件为人读的多行 JSON，而消费侧 `JSONEachRow` 要求单行一条消息（等价真实 log-reader 产出）；按 JSON 原文压缩空白（`json.Compact`，数字字面量不变）后生产。

## 执行步骤

1. 连接 ClickHouse；`RequireKafka` 检查 Kafka 可达（不可达则 Skip）。
2. 建独立临时 topic（4 分区，仅创建不删除，见"清理"）；创建独立测试库并按 setup 顺序建 5 对象（Kafka 表绑定临时 topic）。
3. 改写 timestamp 并压缩后，生产三份 demo 样例到临时 topic。无需等待消费者就绪：实测 ClickHouse Kafka 引擎新消费组从 **earliest** 起点消费（表/MV 创建前已存在的消息也会被消费），生产与消费就绪的时序不影响送达。
4. 轮询明细表（deadline 240s，本机 9p 盘上消费组加入与分区分配可达 1-2 分钟）直至三个样例 logid（`10602749765076101032` / `8877700219231856663` / `12345678901234567890`，均按 UInt64 字面量匹配）全部落库。
5. 断言明细表总行数恰为 3（独立库 + 独立 topic，无重复消费、无历史残留）。
6. 逐 logid 查询单行 18 列断言：
   - level 打平十列（level1Name~level5）：normal = `dep0/rd/dep2/teama/dep3/yyx/'','','',''`；rate_limit = `dep0/rd/dep2/teama/'','','','',''`（level3 为空对象 → ''）；auth_reject 十个全 ''；
   - 限流打平三列：rate_limit = `rlp-0002/tpm/tpm1`；normal 与 auth_reject 全 ''；
   - `log_time` UTC 墙钟：`toUnixTimestamp(log_time)` = 注入的 timestamp，`toString(log_time)` = 该 epoch 的 UTC 格式化（Go 侧 `time.Unix(ts,0).UTC()` 计算）；
   - logid UInt64 原值保留（`toString(logid)` 与样例一致；含超出 Int64 上限的两个取值）；
   - Nullable 语义：`isNull(ai_intent_confidence)`——normal = 0（0.95），rate_limit 与 auth_reject = 1（未分类，NULL）。

## 预期结果

- 步骤 4 在 240s 内等到 3 个 logid 全部落库；步骤 5 行数 = 3。
- 步骤 6 三个 logid 的 18 列断言全部逐项相等（`|` 拼接整行比对）。

## 清理

`t.Cleanup`：`DROP DATABASE <测试库>`；`CLICKHOUSE_IT_KEEP_DB=1` 时保留测试库。
测试 topic **不做删除**：本机 Kafka 数据目录位于 /mnt/d（WSL 9p 文件系统），删除 topic 时 broker 对分区目录的 rename（标记 `*.stray`）会 `AccessDenied`，导致 log dir failed 并使整个 broker 宕机。topic 命名唯一（纳秒后缀）、仅 3 条消息，直接保留。
