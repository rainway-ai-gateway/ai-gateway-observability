# 场景 CLICKHOUSE01：ClickHouse 对接（报表存储新引擎）

## 1. 场景说明

**被测对象**：`ai-gateway-observability/clickhouse/sqls/` 下的六份真实 SQL 资产（不做副本，仅做与 `setup.sh` 一致的 `${VAR}` 变量替换）：建库 `bfe_observability.sql`、明细表 `bfe_ai_request_log.sql`、Kafka 引擎暂存表 `bfe_ai_log_kafka.sql`、消费 MV `bfe_ai_log_load_mv.sql`、聚合表 `bfe_ai_metrics_1m.sql`、聚合 MV `bfe_ai_metrics_1m_mv.sql`。

**背景**：v0.8 在 Doris 链路之外新增 ClickHouse 报表存储引擎（修改说明见 `clickhouse/docs/modifications/2026-10-01-clickhouse-dock/design-changes.md`）。ClickHouse 无 Routine Load / CREATE JOB，等价机制为：

| Doris 机制 | ClickHouse 等价物（本场景被测对象） |
|------------|--------------------------------------|
| Routine Load（Kafka 消费 + COLUMNS 映射打平） | `ENGINE = Kafka` 暂存表 + 消费 MV（JSONExtract 打平 + UTC 换算在 MV SELECT 内完成） |
| `CREATE JOB ... ON SCHEDULE EVERY 1 MINUTE` 分钟聚合 | 明细表上的聚合 MV `TO bfe_ai_metrics_1m`（随插入同步触发，`toStartOfMinute` 对齐分钟桶） |
| 动态分区 7 天保留 | 两表 `TTL ... + INTERVAL 7 DAY` |

**测试环境**：本机 WSL2 单文件 ClickHouse 26.10.1.1149（`environment/clickhouse-installation.md`，HTTP 8123 / Native TCP 9000，内存限 1G），Go 测试经 clickhouse-go stdlib 直连 `127.0.0.1:9000`；TC02 另需本机 WSL2 KRaft 单节点 Kafka 4.3.1（`environment/kafka-installation.md`，`127.0.0.1:9092`）。每个用例使用独立测试库（`<CLICKHOUSE_DATABASE>_it_*`，默认基名 `bfe_observability_test`，结束后 `DROP DATABASE` 清理）。ClickHouse 未启动时全部用例自动 `SKIP`；Kafka 未启动时 TC02 单独 `SKIP`。

**目录与运行**：

```bash
cd ai-gateway-observability/clickhouse/tests/integration
go test ./... -v                                   # 全部
go test ./implementation/scenario-CLICKHOUSE01-clickhouse-dock/ -run TestTC01 -v   # 单例
```

## 3. 关键设计取舍

- **真实 Kafka 链路**：ClickHouse 侧的打平发生在 MV 消费 Kafka 的路径上（等价 Doris Routine Load 的 COLUMNS 映射），因此 TC02 必须用真实生产 → Kafka 引擎 → 消费 MV 链路验证；doris-it 不生产 Kafka 消息（其 TC02 仅校验任务创建被 Doris 接受），此处不对齐。Kafka 不可达时 TC02 单独 Skip。
- **独立临时 topic**：测试消息写入 `<KAFKA_TOPIC>_<纳秒后缀>` 的独立新 topic（显式 4 分区，对齐资产 `kafka_num_consumers = 3`），配套测试消费组，从根上消除位点与残留消息跨运行污染。实测 ClickHouse Kafka 引擎新消费组为 **earliest** 起点（表/MV 创建前已存在的消息也会被消费），故生产无需等待消费者就绪；消费组加入与分区分配在本机 9p 盘上可达 1-2 分钟，轮询 deadline 放宽到 240s。
- **demo 样例的两处消息层改写（不改 demo 文件）**：① `timestamp` 重写为当前时刻——demo 时间戳为 2026-08-24，早于明细表 TTL 7 天，直接消费会写入即被 TTL 静默丢弃；② 多行 JSON 压缩为单行——消费侧 `JSONEachRow` 要求单行一条消息（等价真实 log-reader 产出）。
- **测试 topic 只建不删**：本机 Kafka 数据目录在 /mnt/d（WSL 9p），删除 topic 时 broker 对分区目录的 rename（`*.stray`）会 AccessDenied，导致 log dir failed 并使 broker 宕机；topic 命名唯一、仅 3 条消息，直接保留。
- **TC03/TC05 直插明细**：与 doris-it TC03 同款方式，聚合口径与导入链路解耦验证（导入正确性由 TC02 保证）；聚合 MV 随插入同步触发，无需 Doris JOB 的手动 `INSERT..SELECT` + 固定字面量窗口；插入列清单只含非默认值列（空串/0/空数组由列 DEFAULT 承担，等价 demo 缺失字段语义，同时规避 26.10 master 构建 VALUES 模板推断对「非空字段后的尾部空串 + 复合字面量」错列的已知问题）。
- **SummingMergeTree 查询纪律与排序键全 40 维**：全部聚合断言使用 `GROUP BY <维度> + sum(<指标>)` 兜底（禁止 `SELECT *` 直读）；聚合表 ORDER BY 必须为全 40 维——排序键收窄时后台 merge 会把相同前缀键的行折叠、非排序键维度只保留一行（实测 ai_cache_status 分布 1:2 被污染成 2:1）。TC03 以 `OPTIMIZE TABLE ... FINAL` 强制合并后分布不变作为该纪律的断言点。
- **单语句执行**：六份 SQL 资产均为单语句且以 `${CLICKHOUSE_DATABASE}` 全限定，harness 无需 doris-it 的 `multiStatements=true` 与 `USE <db>` 前缀。
- **幂等清理**：每个用例独立测试库（基名 `CLICKHOUSE_DATABASE` 默认 `bfe_observability_test`，追加用例名与纳秒后缀），`t.Cleanup` 中 `DROP DATABASE`；`CLICKHOUSE_IT_KEEP_DB=1` 可保留现场调试。
- **重建语义差异**：ClickHouse 无 Doris `REPLACE WITH TABLE` 原子换名，TC05 重建为 DROP + CREATE（非原子），通过「先 DROP 聚合 MV 停止增量写入 → DROP 目标表 → 重建 → `INSERT INTO ... SELECT` 明细重算」对齐设计稿的 REPLACE 语义与 §4.3 历史窗口重算语句。
- **集成测试驱动出的资产修复**（已在盘上修复，测试加载修复后版本）：
  1. `bfe_ai_log_load_mv.sql`：Nested 列（req_headers/res_headers）在 MV 按名列匹配时须展开为物理子列 `` `req_headers.key` ``/`` `req_headers.value` ``（Nested 整体名是虚拟投影，直接用 `req_headers` 报 THERE_IS_NO_COLUMN）；
  2. `bfe_ai_metrics_1m.sql`：ORDER BY 从"前六列"修正为全 40 个维度列（原因见上条 merge 污染）。
