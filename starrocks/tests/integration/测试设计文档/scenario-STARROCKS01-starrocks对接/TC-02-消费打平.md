# TC-02 消费打平

## 用例编号与名称

TC-02 消费打平

## 所属场景

STARROCKS01 StarRocks 对接（报表存储新引擎）

## 版本声明

- `ai-gateway-observability`：当前源码版本（v0.8 StarRocks 对接）
- `StarRocks`：本机 WSL2 单机 3.5.21（FE+BE）
- `Kafka`：本机 WSL2 KRaft 单节点 4.3.1（`kafka-installation.md`）

## 测试目的

验证导入链路（等价 Doris Routine Load 的 COLUMNS 映射）：真实 Kafka 消息经 Routine Load 落入明细表，JSON 打平与 UTC 换算口径全部正确——level 打平十列、限流打平三列、`log_time` UTC 墙钟、**布尔两列（`ai_stream` / `is_trust_src_ip`）由 JSON 布尔落成 `0/1`**、NULL 语义；并固化三引擎差异点：SR 对超 Int64 域 logid 直接拒绝（错误行跳过），与 Doris 静默截断、CH UInt64 原值保留均不同。对应设计稿 §4.3 与修改说明 §4.3 / §5。

布尔两列的断言是 **issue #10 的回归守卫**：SR 的 JSON 导入只在 `BOOLEAN` 目标列上把 JSON `true/false` 转成 `1/0`，目标列若是 `TINYINT` 会**静默写 NULL**（`NumberFilteredRows=0`、RL 不报错）。

## 运行模式

端到端链路模式：Go 测试经 segmentio/kafka-go 向 Kafka 真实生产三份 demo 样例，StarRocks Routine Load 消费、COLUMNS 映射打平写入明细表，轮询等待后断言。与 doris-it 的差异：doris-it 不生产 Kafka 消息（其 TC02 仅校验 Routine Load 任务创建被接受）；StarRocks 侧打平发生在 Routine Load 的 COLUMNS 映射路径，必须走真实消费链路。

Kafka 不可达时本用例自动 `SKIP`（其余用例不受影响）。无 Kafka 环境的降级路径（不自动执行，供手工验证）：跳过 Kafka/Routine Load，直接向明细表 INSERT 时手工复现 COLUMNS 表达式（`get_json_string(ai_apikeytags, '$.levelN.x')` 打平列 + `get_json_string(ai_rate_limit_hits, '$[0].xxx')` 限流三列 + `DATE_SUB(FROM_UNIXTIME(...), INTERVAL ...)` UTC 式），等价 RL 列映射求值结果。

## 前置条件

1. StarRocks 已启动，root 无密码可连；Kafka 已启动（`wsl bash /mnt/d/kafka/bin/start-kafka.sh`）。**Kafka 不可达时本用例自动 `SKIP`**。
2. `starrocks/demo/` 下 `normal_request.json` / `rate_limit.json` / `auth_reject.json` 存在（本用例期望值来源，兼校验 demo 文件与 DDL 一致性）。

## 测试步骤

1. `RequireKafka` 检查可达（不可达 Skip）；
2. 创建独立临时 topic `<KAFKA_TOPIC>_<纳秒后缀>`（显式 4 分区，对齐资产 `desired_concurrent_number=3`）；测试 topic 只建不删（本机 9p 盘删 topic 会宕 broker）；
3. 独立测试库中按 setup.sh 顺序建明细表/MV/Routine Load（RL 指向临时 topic 与测试消费组 `starrocks_bfe_ai_log_it`）；
4. RL 创建后检查 `SHOW ALL ROUTINE LOAD`，若状态 PAUSED（本机 9p 盘上 Kafka 元数据获取偶发失败）则执行 `RESUME ROUTINE LOAD FOR bfe_ai_log_load` 自愈；
5. 三份 demo 样例 + **一份"流式"变体**做**消息层改写**后生产（不改 demo 文件）：
   - `timestamp` 重写为当前时刻（demo 的 2026-08-24 早于动态分区 `start=-7` 的既有分区，不重写会成为无分区错误行）；
   - `logid` 重写到 Int64 域（`demoCases`：normal 10602749765076101032→1060274976507610103、rate_limit 8877700219231856663 原值、auth_reject 12345678901234567890→1234567890123456789）——**SR 对超界 BIGINT 直接拒绝**（INSERT 报 "Number out of range"，Routine Load 计错误行跳过）；
   - 第 4 条消息 = normal 样例 + `ai_stream`/`is_trust_src_ip` 改写为 JSON `true`（logid 1060274976507610104）：三份 demo 的这两个字段都是 `false`，只覆盖 0 分支，布尔列需要 1/0 都被断言；
   - 多行 JSON 压缩单行（等价 log-reader 产出格式）；
6. 轮询明细表至全部 logid 落库（deadline 300s，期间每轮检查 RL 状态并自愈 RESUME）；
7. 断言明细表恰好 4 行（独立库 + 独立 topic，无重复消费/历史残留）；
8. 逐 logid 断言单行 20 列：`level1Name~level5` 十列打平值、限流三列、`CAST(logid AS CHAR)`、`TIMESTAMPDIFF(SECOND, '1970-01-01', log_time)`（= 改写后 timestamp 的 epoch——墙钟算术无时区语义；`UNIX_TIMESTAMP(log_time)` 会按会话时区解释、差 8 小时，**禁用**）、`CAST(log_time AS CHAR)`（= timestamp 的 UTC 渲染，**与 FE 会话时区无关**——COLUMNS 算术式减去会话偏移）、`ai_intent_confidence` 的 NULL 标记与值（normal=0.95 非 NULL；rate_limit/auth_reject 为 NULL；未打平层级的 NULL 在断言层按 '' 比较）、**`ai_stream` 与 `is_trust_src_ip` 的取值**（三份 demo=`0`，流式变体=`1`；查询写成 `IF(ai_stream IS NULL,'NULL',IF(ai_stream,'1','0'))`，NULL 会渲染成字面量 `NULL` 从而使断言失败，不会像 `CAST` 那样被吞掉）；
9. **布尔列非空守卫**：`COUNT(*) - COUNT(ai_stream)` 与 `COUNT(*) - COUNT(is_trust_src_ip)` 均须为 0（issue #10 的静默 NULL 只能靠列级非空统计发现）；
10. `t.Cleanup` 删除测试库。

## 预期结果

- 四行样例全部落库，逐列断言与 demo 期望值一致；
- `log_time` 字符串 = `time.Unix(ts,0).UTC()` 渲染（UTC 墙钟口径与 MySQL 链路 log-reader 写入一致）；
- 布尔两列落 `0/1` 且**无非空缺失**：`ai_stream` 三行为 `0`、流式变体为 `1`；`is_trust_src_ip` 同；两列 NULL 行数为 0；
- NULL 语义：未分类请求的 `ai_intent_confidence` 为 NULL（非 0）。

## 备注

- 与 clickhouse-it TC02 的差异：CH 侧 logid 为 UInt64 原值断言（含超 Int64 取值），SR 侧因 BIGINT 拒绝超界值，logid 改写为 Int64 域后断言；该差异属引擎类型系统行为，非资产缺陷（真实上游 logid 在 Int64 范围内，见 TABLE_DESIGN §2.2）。
- RL 消费延迟：本机 9p 盘上消费组加入与分区分配可达 1-2 分钟，deadline 放宽到 300s。
